# Data model

How Cupboard Tracker stores its data in Cosmos DB. Terms follow [domain-language.md](domain-language.md).

Anything marked **Proposal** is not yet agreed. All proposals are collected under [Decisions needing confirmation](#decisions-needing-confirmation) at the end.

---

## Overview

- **Cosmos DB serverless**, one account, **one database**.
- Four data containers plus one infrastructure container for the change feed.
- Single environment, and it is the live household system.
- Volumes are tiny: one household, tens of scans a day, a few hundred units in stock. Partition keys are therefore chosen for **simple, cheap point reads and idempotent writes**, not for scale. Cross-partition queries over this much data are cheap and acceptable.
- All timestamps are UTC, ISO 8601 (`2026-10-16T18:42:07.123Z`). Display in UK local time happens in the UI and emails only.
- Every document has `id` (string) and Cosmos adds `_etag` / `_ts`. `_etag` is used for optimistic concurrency.

| Container | Purpose | Partition key | Lifecycle |
|---|---|---|---|
| `scanEvents` | Raw scans from the Pi | `/deviceId` | Append-only |
| `products` | Product cache keyed by barcode | `/barcode` | Create-once, then updated only by naming / photo identification |
| `inventoryItems` | One document per unit (plus unmatched check-outs) | `/barcode` | Updated in place; soft-deleted (status), never deleted |
| `devices` | One document per logical device | `/deviceId` | Updated in place |
| `leases` | Change-feed processor bookkeeping | `/id` | Managed by the Functions Cosmos DB trigger |

### Who writes and reads what

| Component | `scanEvents` | `products` | `inventoryItems` | `devices` |
|---|---|---|---|---|
| Ingest Function | **write** (create) | – | – | **write** (upsert) |
| API Function: change-feed processor | read (change feed) | read / create | read / create / update | – |
| API Function: HTTP (BFF) | read | read / update (name a product) | read / update (check out, undo) | read |
| API Function: timers (offline alert, daily digest) | read | read | read | read |

Ingest only writes scan events and devices. It never looks up products or creates units.

## Container: `scanEvents`

**Purpose:** the append-only record of every scan the Pi sends. The source of truth for "what happened"; everything else can be rebuilt from it.

**Written by:** Ingest Function. **Read by:** change-feed processor (via change feed), API, digest.

```json
{
  "id": "0b1c3f1e-6d0e-4c0a-9e0a-3a4d7c1f9a21",
  "deviceId": "scanner-in",
  "role": "in",
  "barcode": "5000354900054",
  "scannedAt": "2026-10-16T18:42:07.123Z",
  "receivedAt": "2026-10-16T18:42:08.410Z",
  "clientSha": "e1130b1"
}
```

| Field | Notes |
|---|---|
| `id` | **Scan ID**: UUID generated by the Pi when the scan is read. See [Idempotency](#idempotency). |
| `deviceId` | Logical device that scanned. Partition key. |
| `role` | `in` or `out`, as mapped on the Pi at scan time. Stored on the event so history is not changed by later device changes. |
| `barcode` | Exactly as scanned (validated: digits, length 8 / 12 / 13, valid check digit). |
| `scannedAt` | Pi clock, UTC. Becomes the unit's `checkedInAt` / `checkedOutAt`. |
| `receivedAt` | Server time when ingest stored it. |
| `clientSha` | Deployed Pi client commit. Anything else the Pi sends is stored as-is alongside. |

**Partition key: `/deviceId`.**
- Only two devices, so effectively two logical partitions. Fine at this volume (each partition is limited to 20 GB, far beyond a household's lifetime of scans).
- The scan ID is the document `id`, so a resent scan from the same device lands in the same partition and hits an `id` conflict. That is what makes ingest idempotent.
- The change feed reads across all partitions, so the processor is unaffected.
- Alternative considered: `/barcode`. Rejected because the scan is valid and must be stored even if the barcode is odd, and idempotency is simpler keyed on the device.

**Indexing:** default (all paths) is fine. Queries are by time range for the digest (`scannedAt`).

**Lifecycle:** **append-only**. Never updated, never deleted.

## Container: `products`

**Purpose:** the product cache. One document per barcode, so each barcode is looked up once. Filled by product lookup (Open Food Facts) or by naming / photo identification.

**Written by:** change-feed processor (create), API (name a product / photo identification). **Read by:** change-feed processor, API, digest.

```json
{
  "id": "5000354900054",
  "barcode": "5000354900054",
  "status": "matched",
  "source": "openFoodFacts",
  "displayName": "PG Tips Pyramid Tea Bags 240",
  "brand": "PG Tips",
  "quantity": "696 g",
  "imageUrl": "https://images.openfoodfacts.org/...",
  "fetchedAt": "2026-10-16T18:42:09.002Z",
  "namedAt": null,

  "shelfLifeDays": null,
  "icon": null
}
```

| Field | Notes |
|---|---|
| `id` / `barcode` | The barcode. `id` equals `barcode` so a point read needs no query. |
| `status` | `matched` (found by lookup), `noMatch` (lookup found nothing; display name is `Unknown item (<barcode>)`), `named` (named by hand), `identified` (photo identification). |
| `source` | `openFoodFacts`, `manual`, `photo`. |
| `displayName` | What the stock list shows. Built per the Open Food Facts spike's recommendation. |
| `brand`, `quantity`, `imageUrl` | Optional, from lookup. Exact set to be settled by the Open Food Facts spike. |
| `fetchedAt`, `namedAt` | When lookup / naming happened. |

**Reserved, not used yet:** `shelfLifeDays` (Jev's shelf-life estimate) and `icon`.

**Partition key: `/barcode`.**
- Every access is "product for this barcode", a single-partition point read (`id` + `barcode`).
- One document per partition is fine at this volume; the number of distinct barcodes is in the hundreds.

**Indexing:** default. If listing products by `displayName` is needed, the default range index covers it.

**Lifecycle:**
- **Created once, never overwritten by lookup.** Cached products are kept forever and never re-fetched, so manual names are never lost. Creation is create-if-not-exists, so a race between two scans of a new barcode neither fails nor duplicates.
- A `noMatch` product is later **updated in place** by naming or photo identification (`status` → `named` / `identified`, `displayName`, `source`, `namedAt`).
- Transient lookup failures cache nothing.

## Container: `inventoryItems`

**Purpose:** one document per **unit** (physical item). Stock is the set of units with status `inStock`. Units are created on check-in and marked checked out, never deleted, so undo check-out and the digest's activity both work.

The same container also holds **unmatched check-out** records (see below), distinguished by `type`.

**Written by:** change-feed processor (create unit; check out; record unmatched check-out), API (check out from UI, undo, dismiss, expiry). **Read by:** API, digest, check-out unit selection.

### Unit

```json
{
  "id": "0b1c3f1e-6d0e-4c0a-9e0a-3a4d7c1f9a21",
  "type": "unit",
  "barcode": "5000354900054",
  "status": "inStock",
  "productStatus": "matched",
  "checkInScanId": "0b1c3f1e-6d0e-4c0a-9e0a-3a4d7c1f9a21",
  "checkInDeviceId": "scanner-in",
  "checkedInAt": "2026-10-16T18:42:07.123Z",

  "checkedOutAt": null,
  "checkOutScanId": null,
  "checkOutSource": null,

  "estimatedExpiryDate": null,
  "expiryIsApproximate": null
}
```

| Field | Notes |
|---|---|
| `id` | The **check-in scan ID**, so replays of the same scan can never create a second unit. |
| `type` | `unit`. |
| `barcode` | Partition key. The product is `products` with `id = barcode`. |
| `status` | `inStock` or `checkedOut`. |
| `productStatus` | `matched`, `noMatch` or `lookupFailed` at check-in. `lookupFailed` means Open Food Facts was unavailable after retries; the unit shows as `Unknown item (<barcode>)` and has no product document yet. |
| `checkedInAt` | The scan's `scannedAt`. **This is the bought date**; there is no separate field. |
| `checkedOutAt`, `checkOutScanId` | Set when checked out. **Reserved for the check-out feature; not used until then.** |
| `checkOutSource` | `scanner` or `ui`. Reserved, not used yet. |

**Reserved, not used yet:** `estimatedExpiryDate` and `expiryIsApproximate` (stock-take units), set by the expiry feature. The no-match status is carried by `productStatus` and the product's `status`, not by a field of its own.

**Undo check-out** (reserved for later): set `status` back to `inStock` and clear `checkedOutAt`, `checkOutScanId`, `checkOutSource`.

### Unmatched check-out (**Proposal**)

A `out` scan for a barcode with no unit in stock. Recorded so the future scanners screen can list and dismiss it.

```json
{
  "id": "7d2c9e44-2b1a-4f5e-8d6a-0c3e51a8b7f2",
  "type": "unmatchedCheckOut",
  "barcode": "5010000000000",
  "checkOutScanId": "7d2c9e44-2b1a-4f5e-8d6a-0c3e51a8b7f2",
  "deviceId": "scanner-out",
  "scannedAt": "2026-10-16T19:03:11.000Z",
  "dismissed": false,
  "dismissedAt": null
}
```

The domain language calls this a "no-match check-out" for a barcode that product lookup couldn't resolve. This record covers a wider case: any check-out with no unit to remove, matched product or not. See decision 5.

**Partition key: `/barcode`.**
- The hot query is "in-stock units for barcode X" (check-out selection, count per product). That is a single-partition query.
- Stock list and digest need all in-stock units: a cross-partition query. At hundreds of documents this is trivial and cheap. If the household ever grows into thousands of units, revisit.
- Alternative considered: `/status`. Rejected because the partition key value of a document should not change; moving a unit between partitions on every check-out means delete + create.

**Indexing:** default is fine. If RU use matters later, add a composite index on `(status, checkedInAt)` for selection and `(status, checkedOutAt)` for the digest.

**Lifecycle:** **updated in place**, **soft-deleted** (status `checkedOut`). Units are never deleted.

## Container: `devices`

**Purpose:** one document per logical device (`deviceId`), with its role and last seen.

**Written by:** Ingest Function (upsert on each scan). **Read by:** API (scanners screen), offline-alert timer.

```json
{
  "id": "scanner-in",
  "deviceId": "scanner-in",
  "role": "in",
  "lastSeenAt": "2026-10-16T18:42:08.410Z",
  "lastScanAt": "2026-10-16T18:42:07.123Z"
}
```

| Field | Notes |
|---|---|
| `id` / `deviceId` | The logical device ID from the Pi's env mapping. |
| `role` | `in` or `out`. If an existing device's role changes, ingest updates it and logs a warning. |
| `lastSeenAt` | Server receive time of the last scan or heartbeat. Server time, not the Pi clock, so a wrong Pi clock cannot hide an outage. |
| `lastScanAt` | `scannedAt` of the latest scan. |

**Partition key: `/deviceId`.** Access is always by device; a handful of documents.

**Indexing:** default.

**Lifecycle:** **updated in place** (upsert). Not deleted.

**Note on heartbeats and the hub:** heartbeat handling will be defined by the heartbeat feature and may add a `kind` field or a separate document type for the Pi itself. That is out of scope here.

## Container: `leases` (infrastructure)

Used by the Azure Functions Cosmos DB trigger to track its position in the `scanEvents` change feed. Not a domain container; no application code reads or writes it.

- Partition key `/id`.
- Created by the Bicep baseline, since the change-feed processor depends on it.

## Change-feed flow

The API Function app processes new scan events through a Cosmos DB trigger on `scanEvents` (with the `leases` container). Ingest does not do any of this.

```
Pi ──POST /api/scans──▶ Ingest ──▶ scanEvents (create, id = scan ID)
                                   devices    (upsert)

scanEvents change feed ──▶ API Function (processor), for each new event:

  role = in:
    1. products.read(barcode)
         hit  ──▶ use it (no Open Food Facts call)
         miss ──▶ Open Food Facts lookup
                    found     ──▶ products.create (matched)
                    not found ──▶ products.create (noMatch, "Unknown item (<barcode>)")
                    transient failure ──▶ retry (back-off); still failing ──▶
                                          no product cached, unit.productStatus = lookupFailed, error logged
    2. inventoryItems.create unit (id = scan ID; conflict = already processed, skip)
    3. notifications (scan feed / SignalR) ──▶ later feature

  role = out:
    1. select one inStock unit for the barcode (see unit selection)
         found ──▶ mark checkedOut (ETag-guarded), set checkOutScanId
         none  ──▶ create unmatchedCheckOut record
    2. notifications ──▶ later feature
```

The change feed is **at-least-once**, so every step must be safe to repeat. See Idempotency.

## Unit selection on check-out (**Proposal**)

When several units share a barcode, a check-out takes **one**, chosen by:

1. Among `inStock` units with the scanned barcode, **soonest `estimatedExpiryDate` first** (units with an estimate before units without).
2. Ties and units with no estimate: **oldest `checkedInAt` first** (FIFO).
3. Final tie-break: lowest `id`, so the choice is deterministic.

This is "use the oldest stuff first". While no expiry dates exist, it is plain FIFO. Needs Gary's confirmation.

**Concurrency:** two quick check-outs of the same barcode must take two different units. The update is conditional on the unit's `_etag`. On conflict, the processor re-reads and tries the next candidate.

## Idempotency

**Scan ID scheme (Proposal):** the Pi generates a **UUID v4 per scan** at the moment it reads the barcode, before queueing. It is the scan event's `id`, and it travels with the event through retries and resends.

| Situation | What happens |
|---|---|
| Pi resends a scan (timeout, lost response, queue replay) | Ingest `create`s with `id = scan ID`. A conflict is treated as success and returns the same 2xx. One document stored. |
| Change feed replays an event | Check-in: unit `id` is the scan ID, so a second create conflicts and is skipped. Check-out: before acting, look for a unit or unmatched record that already has `checkOutScanId = scan ID`; if found, do nothing. |
| Two scans of the same tin | Two different scan IDs, so two units. This is intended ("one unit per scan"). |
| Product lookup repeated | Product create is create-if-not-exists; existing products are never overwritten. |

Note this means a *genuine* second scan is never mistaken for a resend, because the ID is minted per read, not derived from barcode + time.

## Fields reserved for later features

None of these are written or read yet. They are listed so the first features leave room for them.

| Field | Container | For |
|---|---|---|
| `estimatedExpiryDate`, `expiryIsApproximate` | `inventoryItems` | Estimated expiry (Jev), stock-take |
| `checkedOutAt`, `checkOutScanId`, `checkOutSource` | `inventoryItems` | Check-out, undo check-out, digest activity |
| `unmatchedCheckOut` document, `dismissed`, `dismissedAt` | `inventoryItems` | Scanners screen, dismiss |
| `shelfLifeDays` | `products` | Shelf life estimate (Jev) |
| `icon` | `products` | Stock list icon |
| `status` values `named`, `identified` | `products` | Name a product, photo identification |

`bought date` has no field of its own: it is `checkedInAt`.

## Decisions needing confirmation

1. **Unit selection on check-out.** Soonest estimated expiry first, then oldest `checkedInAt` (FIFO), then `id`. OK?
2. **Scan ID.** Pi-generated UUID v4 per scan, used as the scan event `id` and the check-in unit `id`. OK? (Alternative: server-assigned IDs, which would lose idempotency for resends.)
3. **Partition keys.** `scanEvents` → `/deviceId`, `products` → `/barcode`, `inventoryItems` → `/barcode`, `devices` → `/deviceId`. OK, given the tiny volumes?
4. **Bought date.** Stored as `checkedInAt` rather than a separate field. OK?
5. **Unmatched check-outs.** Stored as `type: unmatchedCheckOut` documents in `inventoryItems`, covering any check-out with no unit in stock. The domain language's "no-match check-out" is narrower (unresolved barcode), so that term needs aligning. Alternative: a fifth container.
6. **`lookupFailed` units.** A unit created while Open Food Facts was down has `productStatus: lookupFailed` and no product document. Should something retry the lookup later, or does naming by hand cover it?
7. **`leases` container.** Included as the fifth, infrastructure container in the Bicep baseline. The card says "four containers"; this is the one extra.
