# Data model

How Cupboard Tracker stores its data in Cosmos DB. Terms follow [domain-language.md](domain-language.md).

All decisions in this document are agreed with Gary. They're listed under [Decisions](#decisions) at the end.

---

## Overview

- **Cosmos DB serverless**, one account, **one database**.
- **Data containers** plus one infrastructure container for the change feed, all created by the Bicep (`sentDigests` was added by #46; `settings` by #120, below, with the later containers).
- Single environment, and it is the live household system.
- Volumes are tiny: one household, tens of scans a day, a few hundred units in stock. Partition keys are therefore chosen for **simple, cheap point reads and idempotent writes**, not for scale. Cross-partition queries over this much data are cheap and acceptable.
- **A product's identity is its own `productId`, not a barcode.** Loose items (fruit, bakery, deli) are products with no barcode, and one product can have several barcodes. Barcodes are an optional way to find a product, through [barcode lookup](#barcode-lookup-document) documents.
- **Barcodes are stored exactly as scanned**, everywhere: no zero-padding, trimming of leading zeros or other normalising. Open Food Facts returns 12-digit UPC-A codes padded to 13 digits; that never changes our keys.
- All timestamps are UTC, ISO 8601 (`2026-10-16T18:42:07.123Z`). Display in UK local time happens in the UI and emails only.
- Every document has `id` (string) and Cosmos adds `_etag` / `_ts`. `_etag` is used for optimistic concurrency.

| Container | Purpose | Partition key | Lifecycle |
|---|---|---|---|
| `scanEvents` | Raw scans from the Pi | `/deviceId` | Append-only |
| `products` | Products (the product cache), plus barcode lookup documents | `/id` | Products updated in place; barcode lookups create-once |
| `inventoryItems` | One document per unit | `/productId` | Updated in place; soft-deleted (status), never deleted |
| `devices` | One document per scanner's logical device, plus one per hub (`kind: "hub"`) | `/deviceId` | Updated in place |
| `unmatchedCheckOuts` | Check-out scans with no unit in stock | `/id` | Created once; updated only to dismiss |
| `sentDigests` | One record per daily digest sent (or being sent) | `/id` | Created once per day; deleted only if that day's send fails |
| `leases` | Change-feed processor bookkeeping | `/id` | Managed by the Functions Cosmos DB trigger |

### Who writes and reads what

| Component | `scanEvents` | `products` | `inventoryItems` | `devices` | `unmatchedCheckOuts` |
|---|---|---|---|---|---|
| Ingest Function | **write** (create) | – | – | **write** (upsert on scans; hub on heartbeats) | – |
| API Function: change-feed processor | read (change feed) | read / create / update (lookup retry) | read / create / update | – | create |
| API Function: HTTP (BFF) | read | read / create (loose items) / update (name a product) | read / create (loose items) / update (check out, undo) | read | read / update (dismiss) |
| API Function: lookup-retry timer | – | read / update | – | – | – |
| API Function: shelf-life timer (#52) | – | read / update (shelf life) | read / update (`estimatedExpiryDate`) | – | – |
| API Function: offline-alert timer | – | – | – | read hubs / update (`offlineAlertSentAt`) | – |
| API Function: daily-digest timer (also creates its `sentDigests` record) | – | read | read | – | – |

Ingest only writes scan events, devices and hubs. It never looks up products or creates units.

## Container: `scanEvents`

**Purpose:** the append-only record of every scan the Pi sends. The source of truth for "what happened"; everything else can be rebuilt from it.

**Written by:** Ingest Function. **Read by:** change-feed processor (via change feed), API, digest.

```json
{
  "id": "0b1c3f1e-6d0e-4c0a-9e0a-3a4d7c1f9a21",
  "deviceId": "scanner-in",
  "role": "in",
  "barcode": "5000354900054",
  "scannedAt": "2026-10-16T18:42:07.123Z",
  "receivedAt": "2026-10-16T18:42:08.410Z",
  "clientSha": "e1130b1"
}
```

| Field | Notes |
|---|---|
| `id` | **Scan ID**: UUID v4 generated by the Pi when the scan is read. See [Idempotency](#idempotency). |
| `deviceId` | Logical device that scanned. Partition key. |
| `role` | `in` or `out`, as mapped on the Pi at scan time. Stored on the event so history is not changed by later device changes. |
| `barcode` | Exactly as scanned (validated: digits, length 8 / 12 / 13, valid check digit). |
| `scannedAt` | Pi clock, UTC. Becomes the unit's `checkedInAt` / `checkedOutAt`. |
| `receivedAt` | Server time when ingest stored it. |
| `clientSha` | Deployed Pi client commit. Anything else the Pi sends is stored as-is alongside. |

**Partition key: `/deviceId`.**
- Only two devices, so effectively two logical partitions. Fine at this volume (each partition is limited to 20 GB, far beyond a household's lifetime of scans).
- The scan ID is the document `id`, so a resent scan from the same device lands in the same partition and hits an `id` conflict. That is what makes ingest idempotent.
- The change feed reads across all partitions, so the processor is unaffected.
- Alternative considered: `/barcode`. Rejected because the scan is valid and must be stored even if the barcode is odd, and idempotency is simpler keyed on the device.

**Indexing:** default (all paths) is fine. Queries are by time range for the digest (`scannedAt`).

**Lifecycle:** **append-only**. Never updated, never deleted.

## Container: `products`

**Purpose:** the **product cache**. One **product** document per product, each with its own `productId`, plus one **barcode lookup** document per known barcode. Products are filled by product lookup (Open Food Facts), by naming, by photo identification, or by adding a loose item.

Both document types live here, told apart by `type`.

**Written by:** change-feed processor (create on check-in; lookup retry on the next check-in), lookup-retry timer, API (name a product, photo identification, add a loose item, edit details). **Read by:** change-feed processor, API, digest, timers.

### Product

A product found on Open Food Facts:

```json
{
  "id": "3f6c2a8e-9b14-4e1d-8a52-7c0d1e9f4b36",
  "type": "product",
  "status": "known",
  "source": "openFoodFacts",
  "barcodes": ["5000354922831"],
  "displayName": "Beef Gravy",
  "brand": "Bisto",
  "size": "230g",
  "imageUrl": "https://images.openfoodfacts.org/images/products/500/035/492/2831/front_en.3.200.jpg",
  "categoryTags": ["en:groceries", "en:sauces", "en:gravy"],
  "fetchedAt": "2026-10-16T18:42:09.002Z",
  "lookupAttempts": 1,
  "lastLookupAttemptAt": "2026-10-16T18:42:09.002Z",

  "namedAt": null,
  "namedBy": null,
  "shelfLifeDays": 365,
  "shelfLifeSource": "jev",
  "shelfLifeConfidence": 0.65,
  "jevLowConfidence": false,
  "storage": "cupboard",
  "shelfLifeEstimatedAt": "2026-10-16T18:45:00.120Z",
  "icon": null
}
```

A **loose item** (no barcode), added from the app:

```json
{
  "id": "a91d7f02-5c3b-4b8e-9e61-2f4c8d0b7a15",
  "type": "product",
  "status": "known",
  "source": "manual",
  "barcodes": [],
  "displayName": "Bananas",
  "brand": null,
  "size": null,
  "namedAt": "2026-10-17T09:12:44.310Z",
  "namedBy": "<Entra object ID>",
  "lastAddedAt": "2026-10-18T09:12:44.310Z"
}
```

A barcode that Open Food Facts couldn't be reached for (`lookupFailed`) looks like the first example with `status: "lookupFailed"`, `source: null`, `displayName: "Unknown item (<barcode>)"`, no Open Food Facts fields, and `lookupAttempts` / `lastLookupAttemptAt` recording the failed attempts. A `noMatch` product looks the same with `status: "noMatch"`.

| Field | Notes |
|---|---|
| `id` | **`productId`**: a GUID minted when the product is created. Partition key. Units refer to it. |
| `type` | `product`. |
| `status` | `known` (we have a name), `noMatch` (Open Food Facts doesn't know this barcode; final), `lookupFailed` (Open Food Facts couldn't be reached; retried, see [Lookup failures](#lookup-failures)). |
| `source` | Where the current name came from: `openFoodFacts`, `manual` (named or edited by hand, or a loose item typed or picked), `photo` (a loose item first added from a photo, #58). `null` while `noMatch` / `lookupFailed`. |
| `barcodes` | Zero or more barcodes, **exactly as scanned**. Each has a barcode lookup document. Empty for a loose item. |
| `displayName` | What the stock list shows. `Unknown item (<barcode>)` for `noMatch` / `lookupFailed`. From Open Food Facts: see below. |
| `brand` | Optional. From Open Food Facts: the first entry of `brands`, trimmed. |
| `size` | Optional. From Open Food Facts: `quantity`, trimmed, kept as free text and never parsed (it's inconsistent: "230g", "2 x 130 g", "250"). |
| `imageUrl` | Optional. From Open Food Facts: `image_front_small_url`, else `image_front_url`. |
| `categoryTags` | Optional. From Open Food Facts: `categories_tags` (e.g. `en:gravy`). A hint for the shelf-life estimate later. |
| `fetchedAt` | When Open Food Facts answered with this product. |
| `lookupAttempts`, `lastLookupAttemptAt` | How many times product lookup has been tried for this product, and when last. Used by the lookup-retry timer. |
| `lookupFailedSince` | When the product first became `lookupFailed` (cleared once resolved). The timer logs an **error** if it's still failing 24 hours later. |
| `feedDismissedAt` | When someone last dismissed its amber "No match" toast in the scan feed (#54, `POST /api/scan-feed/{id}/dismiss`). Shared by the household. Only hides the toast: a check-in after this time shows it again. Absent until dismissed. |
| `lastAddedAt` | When units were last added to it in the app (#58): orders the Add screen's quick pick. Best-effort, ETag-guarded. Absent until then. |
| `namedAt`, `namedBy` | When and by whom (for a loose item: who first added it) (Entra object ID) the product was named by hand. Written by naming an unknown item (#51, `PUT /api/products/{id}/name`): only while the product is still `noMatch` / `lookupFailed`, with an ETag-guarded replace, so it and the lookup-retry timer can't overwrite each other. Once named it's `known`, so check-ins never look it up again. |

**Display name from Open Food Facts** (decided in [spike #28](spikes/28-open-food-facts.md)): `product_name_en`, else `product_name`, trimmed, otherwise **exactly as returned**. No title-casing, no language checks. A product with neither is a no-match.

**Shelf life** (#52, [spike #40](spikes/40-jev.md)): how long the product usually keeps after it's bought, unopened and stored the usual way. Estimated **once per product**, only for `known` products (unknown items get none); absent or `null` until then.

| Field | Notes |
|---|---|
| `shelfLifeDays` | The estimate in days: one of Jev's ten worded levels (2, 4, 7, 14, 30, 90, 180, 365, 730, 1095). |
| `shelfLifeSource` | `jev`, or `manual` when set in item detail (#53, `PUT /api/products/{id}/shelf-life`; confidence 1). Jev never overwrites a manual shelf life, and a manual one applies to units bought from then on. |
| `shelfLifeConfidence` | Jev's confidence in the score, 0–1. |
| `jevLowConfidence` | `true` when that confidence was below **0.5**, so the cautious **25th-percentile** level was used instead of the median. |
| `storage` | The **usual storage** Jev chose: `cupboard`, `fridge` or `freezer`. The estimate is for that storage. Not shown in the UI yet. |
| `shelfLifeEstimatedAt` | When it was estimated. |

Written only by the **shelf-life timer**, with an ETag-guarded replace that applies only while the product is still `known` with no shelf life.

**Edited details** (#53, `PUT /api/products/{id}/details`): a known product's name, brand and size corrected in item detail. It sets `source: manual` plus `editedAt` and `editedBy` (Entra object ID), ETag-guarded. Known products are never looked up again, so nothing overwrites the edit.

**Opened, frozen and defrosted (#65):** how long the product keeps in each state, from Jev on the shelf-life timer (step 3 below), so marking a unit is instant.

| Field | Notes |
|---|---|
| `openedShelfLifeDays`, `openedStorage` | How long it keeps **once opened**, and where (`cupboard` / `fridge` / `freezer`). |
| `frozenShelfLifeDays` | How long it keeps **in the freezer**, frozen the day it was bought. |
| `defrostedShelfLifeDays`, `defrostedStorage` | How long it keeps **once defrosted**, and where (`cupboard` / `fridge`). |
| `…ShelfLifeSource`, `…ShelfLifeConfidence`, `…LowConfidence` | Per state, as for the shelf life. `openedShelfLifeSource: manual` when set in item detail (`PUT /api/products/{id}/opened-shelf-life`); Jev never overwrites it. |
| `stateEstimatedAt` | When Jev answered. Absent until then (the timer's query). |

**Aisle and icon (#71, #72):**

| Field | Notes |
|---|---|
| `aisle`, `aisleSource`, `aisleConfidence`, `aisleEstimatedAt` | The product's aisle ID (one of the 14 in `Aisles.cs`), `jev` or `manual` (`PUT /api/products/{id}/aisle`; never overwritten), Jev's confidence, and when. Absent until classified: the stock list shows it under **Other**. |
| `icon`, `iconSource`, `iconConfidence`, `iconEstimatedAt` | The icon name (one of `ProductIcons.Names`), `jev` or `manual`, confidence, when. `icon` is absent when Jev was below 0.3; `iconSource` present means "answered". "Let Jev choose" removes all four, so the timer asks again. |

**Reserved, not used yet:** `icon`.

### Store-label check-in (#58)

A check-in scan of an in-store printed label (see [domain language](domain-language.md#identification)). It's never looked up and makes no product: it waits here until someone says what it is.

```json
{
  "id": "storeLabel:0b1c3f1e-6d0e-4c0a-9e0a-3a4d7c1f9a21",
  "type": "storeLabelCheckIn",
  "scanId": "0b1c3f1e-6d0e-4c0a-9e0a-3a4d7c1f9a21",
  "barcode": "2012345678903",
  "deviceId": "scanner-in",
  "scannedAt": "2026-10-18T09:00:00.000Z",
  "recordedAt": "2026-10-18T09:00:01.250Z",
  "resolvedAt": null,
  "resolvedProductId": null,
  "resolvedBy": null,
  "feedDismissedAt": null
}
```

- `id` is `storeLabel:` plus the scan ID, created **if not exists**, so a change-feed replay never records it twice.
- **Assigning** (`POST /api/store-label-check-ins/{scanId}/assign`) creates one unit (id = the scan ID, `checkedInAt` = `scannedAt`, `barcode` = the label, `checkedInBy` = the user) and sets `resolvedAt`, `resolvedProductId` and `resolvedBy` (ETag-guarded). The label's barcode is **never** given a barcode lookup: the next pack with the same label is a new question.
- `feedDismissedAt`: hidden from the scan feed (still on the scanners screen).
- Lives in `products` (a handful of small documents, partition `/id`) rather than a container of its own.

### Generic name (#90)

One document per **generic name** (what you'd say to someone going to the shop: "Semi-skimmed milk"), shared by every product of that kind. Kept in `products` as a document kind rather than a container of its own, so no infrastructure change was needed; every product query already filters on `type`.

```json
{
  "id": "generic:semi-skimmed milk",
  "type": "genericName",
  "name": "Semi-skimmed milk",
  "aisle": "dairyEggs",
  "createdAt": "2026-10-19T21:30:00.000Z",
  "createdBy": "foundry",
  "addWhenOut": true,
  "addWhenOutBy": "<oid>",
  "addWhenOutAt": "2026-10-20T20:00:00.000Z"
}
```

- **`id`** is `generic:` plus the normalized name (lower case, trimmed, single spaces). Created with a create-only write, so two products can never make two records for the same name: the second one finds the first.
- **`aisle`** comes from the product that created it; matching starts in the product's aisle.
- **`createdBy`**: `foundry` (written by the timer) or `manual` (typed in Edit details).
- **`addWhenOut`** (#89): put the name on the shopping list when nothing is left in stock across every product with this generic name. Missing means off. Set with a patch (`addWhenOutBy`, `addWhenOutAt`: who and when), so it's household-wide and follows the name, not a product.

On each **product**: `genericName` (display), `genericNameId` (the record's normalized id), `genericNameSource` (`jevMatch` | `foundry` | `manual` | `fallback`), `genericNameConfidence` (Jev's, when matched) and `genericNameEstimatedAt`. Filled by the estimate timer after the aisle is known; `manual` is never overwritten.

**Animal content (#112)**, on each known **product**: `animalContent` (`meat` | `fish` | `none` | `unknown`), `animalContentSource` (`aisle` | `openFoodFacts` | `jev` | `manual`), `animalContentConfidence` (Jev's, when it answered) and `animalContentAt`. Whether the product is or contains meat or fish, or is made from them (stock cubes, meat gravy, lard, gelatine, anchovy sauces); cheese and rennet, eggs, milk and honey are not. Fish counts as meat for "veg", but the value says which. Worked out once by the estimate timer after the aisle is known, in order: the **Meat & fish aisle** → Jev's choice between meat and fish only (`aisle`); otherwise **decisive Open Food Facts categories** (vegetarian / vegan / meat-analogue → `none`, fish or seafood → `fish`, meat → `meat`; only `categoryTags` are cached, not labels or ingredients) (`openFoodFacts`); otherwise **Jev's** meat / fish / neither choice (`jev`), stored as `unknown` below confidence 0.6. Set by hand in Edit details as `manual`, never overwritten. The timer's first runs after #112 were the backfill (40 products a run, every 5 minutes).

### Barcode lookup document

Maps one barcode to its product, so "which product is this barcode?" is a single point read.

```json
{
  "id": "barcode:5000354922831",
  "type": "barcodeLookup",
  "barcode": "5000354922831",
  "productId": "3f6c2a8e-9b14-4e1d-8a52-7c0d1e9f4b36",
  "createdAt": "2026-10-16T18:42:08.950Z"
}
```

| Field | Notes |
|---|---|
| `id` | `barcode:` plus the barcode **exactly as scanned**. Partition key (the container's `/id`). |
| `type` | `barcodeLookup`. |
| `barcode` | The barcode, exactly as scanned. |
| `productId` | The product this barcode belongs to. **Never repointed** (a future merge-products feature would have to handle that explicitly). |

**Why it lives in `products`, not its own container:** it's part of the product cache and is always read together with a product. Keeping it here means one container to provision, back up and grant access to, and the partition key `/id` works for both document types. A separate container would only add a seventh container to Bicep for no gain at this volume.

**Why it makes new-barcode races safe:** the lookup document's `id` is derived from the barcode, and with partition key `/id` an `id` is unique across the container. Creating it with **create-if-not-exists** is therefore a claim on the barcode: when two scans of a new barcode race, exactly one create succeeds. The loser gets a conflict, reads the winner's lookup document and uses its `productId`. See [Change-feed flow](#change-feed-flow).

### Partition key: `/id`

- **Products:** every access by product is a point read by `productId` (the unit says which product it is). Naming a product updates one document; units are untouched, because they reference `productId`, not a name.
- **Barcode lookups:** a point read by `barcode:<digits>`, and the `id` uniqueness above.
- Lists of products (by status for the lookup-retry timer, or by id for the stock list) are **cross-partition** queries. At a few hundred products they are cheap.
- Alternative considered: `/barcode`. Rejected because loose items have no barcode and a product can have several barcodes.

**Indexing:** default. Queries filter on `type` and `status`.

### Lifecycle

- **Barcode lookups are created once and never changed.**
- **Products are never overwritten by product lookup once they have a final answer** (`known` or `noMatch`). Cached products are kept forever and never re-fetched, so manual names are never lost.
- A `lookupFailed` product is **updated in place** by a retry: to `known` (with the Open Food Facts fields) or `noMatch`, or left as `lookupFailed` with a higher `lookupAttempts`.
- A `noMatch` or `lookupFailed` product is **updated in place** by naming or photo identification (`status: known`, `source: manual` / `photo`, `displayName`, `brand`, `size`, `namedAt`, `namedBy`).
- Products are not deleted.

### Lookup failures

When Open Food Facts is down or rate-limited (timeouts, 5xx, 429; see [spike #28](spikes/28-open-food-facts.md#errors)) after the Functions retry policy, check-in still creates the product, with `status: lookupFailed`, and its barcode lookup document, so the unit always has a `productId` and stock is never lost. An error is logged.

`lookupFailed` is **not** a final answer. It's retried by:
- **The lookup-retry timer**, every **15 minutes**: query products with `status = 'lookupFailed'`, and retry Open Food Facts for each (using the first barcode in `barcodes`), at most **10 products per run**, oldest `lastLookupAttemptAt` first.
- **Open Food Facts throttle:** at most `OFF_MAX_REQUESTS_PER_MINUTE` calls a minute (default **12**, Gary's choice; Open Food Facts allows 15 per IP). The change-feed processor effectively runs as one instance (the small scan-events container has one lease) and the timer is a singleton, so the budget is **split**: the timer gets a fifth (2 a minute at the default) and check-in processing the rest (10). Over budget, a caller **waits** for a slot rather than failing, so a stock-take queues.
- **The next check-in of that barcode**, which retries once before creating the unit.

Each retry ends in `known` (found), `noMatch` (not found; final) or `lookupFailed` again (`lookupAttempts` + 1). **Naming by hand also resolves it**, and a named product is never retried. `noMatch` and named products are final and never re-fetched.

### Shelf life and estimated expiry dates (#52)

**The shelf-life timer**, every **5 minutes** (API app, `estimateShelfLives`):

1. Query `known` products with no `shelfLifeDays` (cross-partition), at most **20 per run**, and ask Jev for each: a `score` over the ten worded durations plus a `choice` of usual storage, in one request ([spike #40](spikes/40-jev.md)). Store the shelf-life fields above.
2. Query in-stock units with no `estimatedExpiryDate` (cross-partition) and, for those whose product now has a shelf life, set it (ETag-guarded; a unit checked out meanwhile is skipped). Units opened, frozen or defrosted wait for step 4 instead.
3. **State estimates (#65):** query `known` products with a shelf life but no `stateEstimatedAt`, at most **20 per run**, and ask Jev five questions in **one request** (`docs/spikes/65-jev-unit-state.py`): where to keep it once opened, and how long it keeps once opened, in the freezer, and once defrosted (and where). Same level rule as the shelf life. A manual "once opened" is kept. This also filled existing stock on the first runs after deploy (no separate backfill).
4. Query units with `estimatePending: true` and, where their product now has the estimate for their state, set the date and storage.
5. **Aisle and icon (#71, #72):** query `known` products with no `aisle` or no `iconSource`, at most **40 per run**, and ask Jev in **one request** whatever's missing: a `choice` over the 14 aisles (with short descriptions) and a `choice` over the 131 curated IconPark icons ([spike #60](spikes/60-iconify-icons.md)). A manual aisle or icon is never asked again or overwritten. An icon below **0.3** confidence is stored with no name (`iconSource: jev`, no `icon`), so it isn't asked again and the UI shows the aisle's icon. No separate backfill: existing products are filled over the first runs.

Each step takes at most **40 products per run** (raised from 20 for the initial stock take); runs never overlap.

This covers every way a product becomes known: Open Food Facts at check-in, the lookup-retry timer, and naming in the app. It also did the **one-off fill** of existing stock on the first runs after deploy. Check-in and naming never wait for Jev. **If Jev is unreachable** (429/529, 5xx or timeouts after 3 tries) the run logs a warning and stops; products stay unestimated and the next run tries again. A refused request (400/401/413/415/422) logs an error. With no key yet (`JEV_API_KEY` unresolved), it logs a warning and does nothing. Everything it writes is derived data, and a re-run changes nothing already done.

## Container: `inventoryItems`

**Purpose:** one document per **unit** (physical item). Stock is the set of units with status `inStock`. Units are created on check-in and marked checked out, never deleted, so undo check-out and the digest's activity both work.

**Written by:** change-feed processor (create unit; check out), API (add a loose item; check out from the UI, undo, expiry). **Read by:** API, digest, check-out unit selection.

```json
{
  "id": "0b1c3f1e-6d0e-4c0a-9e0a-3a4d7c1f9a21",
  "productId": "3f6c2a8e-9b14-4e1d-8a52-7c0d1e9f4b36",
  "barcode": "5000354922831",
  "status": "inStock",
  "checkInScanId": "0b1c3f1e-6d0e-4c0a-9e0a-3a4d7c1f9a21",
  "checkInDeviceId": "scanner-in",
  "checkedInAt": "2026-10-16T18:42:07.123Z",

  "checkedOutAt": null,
  "checkOutScanId": null,
  "checkOutSource": null,
  "checkedOutBy": null,

  "estimatedExpiryDate": "2027-10-16",
  "expiryIsApproximate": null
}
```

| Field | Notes |
|---|---|
| `id` | For a scanned unit (and an assigned store label), the **check-in scan ID**, so replays of the same scan can never create a second unit. Units added in the app get an id derived from the add's `requestId`, so a retried add creates nothing twice. |
| `productId` | The unit's product. **Partition key.** |
| `barcode` | Optional. The barcode it was scanned with, exactly as scanned. `null` for units added in the app with no barcode (loose items). |
| `status` | `inStock` or `checkedOut`. |
| `checkInScanId`, `checkInDeviceId` | The scan and device that checked it in. `null` for units added in the app; a store-label unit keeps its scan (#58). |
| `checkInSource`, `checkedInBy` | For units added in the app (#58): `ui` and the user's Entra object ID. A store-label unit has `checkInSource: "scanner"` and the user who assigned it. Absent on scanned units. |
| `checkedInAt` | The scan's `scannedAt` (or the time it was added in the app). **This is the bought date**; there is no separate field. |
| `checkedOutAt`, `checkOutScanId` | Set when checked out: the check-out scan's `scannedAt` and ID, or for a check-out in the app the time it happened and `checkOutScanId: null`. |
| `checkOutSource` | `scanner` (check-out scans) or `ui` (check-out from the stock list, #50). |
| `checkedOutBy` | For `ui` check-outs, the user's Entra object ID (`oid`); `null` for scanner check-outs. |
| `estimatedExpiryDate` | `YYYY-MM-DD` (#52): the **bought date** (`checkedInAt` as a UK calendar date, Europe/London) plus the product's `shelfLifeDays`. Absent or `null` until the product has a shelf life. Set at check-in if the product already has one; otherwise filled in by the shelf-life timer. Changed afterwards only by a person, in item detail. |
| `expirySource` | Where that date came from (#53): `shelfLife`, or `manual` when set in item detail (`PUT /api/units/{id}/estimated-expiry`). A manual date is never recalculated. Since #65 also `opened`, `frozen` or `defrosted`: the unit's latest state (kept even before the date is filled in). Absent on dates written before #53, which all came from the shelf life. |
| `openedOn`, `frozenOn`, `defrostedOn` | `YYYY-MM-DD` (UK) when the unit was marked opened, frozen or defrosted in item detail (#65). In the freezer now = `frozenOn` set and `defrostedOn` absent. Absent otherwise. |

| `estimatePending` | `true` while its state's estimate is missing from the product: the date is the old one until the shelf-life timer fills it in. Absent otherwise. |
| `lastConfirmedAt`, `lastConfirmedVia` | "Still got this?" (#94): when someone last said the unit is still here, and how (`prompt`; #98 adds `stockCheck`). It stops asking until `STILL_HERE_ASK_AGAIN_DAYS` (default 2) UK days later. Absent until then, and removed by Undo. |
| `checkOutReason` | Why it was checked out (#94): `stockCheck` for **Gone** on a "Still got this?" prompt (a correction: counts as running out, pushes nobody). Absent for an ordinary check-out (used), and cleared by Undo check-out. |
| `beforeStateChange` | The estimate fields (`estimatedExpiryDate`, `expirySource`, the three dates, `currentStorage`, `estimatePending`) as they were before the last state change, for **Undo** (`POST /api/units/{id}/undo-state-change`), with the snapshot before that in `before` (up to 5 deep), so each change can be undone in turn. Absent when there's nothing to undo. Cleared fields are **removed** from the document, so Undo never leaves an old value behind. |

The unit doesn't copy the product's status or name: the product is always one point read away. (The earlier `productStatus` field is gone, because every unit now has a product, including `lookupFailed` ones.)

**Reserved, not used yet:** `expiryIsApproximate` (stock-take units). Units from the stock-take get ordinary estimates like any other (decided with Gary: approximate is fine).

**Undo check-out** (#50, `POST /api/units/{unitId}/undo-check-out`): set `status` back to `inStock` and clear `checkedOutAt`, `checkOutScanId`, `checkOutSource` and `checkedOutBy`, so the unit is exactly as before. ETag-guarded; undoing a unit already in stock changes nothing. Check-out from the app uses the same selection rule and ETag handling as a check-out scan, so the app and a scanner never take the same unit.

**Partition key: `/productId`.**
- The hot queries are per product: "in-stock units of product X" (check-out selection, item detail, counts). Single-partition.
- Every unit has a product, including loose items and `lookupFailed` scans, so the key is always present.
- The check-in idempotency rule holds because a scan's barcode always resolves to the same `productId` (barcode lookups are never repointed), so a replayed scan lands in the same partition and conflicts on `id`.
- Stock list and digest need all in-stock units, or all units checked in or out in a time window: **cross-partition** queries. At hundreds of documents these are trivial.
- Alternatives considered: `/barcode` (rejected: loose items have none, and a product's units would be split across its barcodes); `/status` (rejected: the partition key value of a document should not change).

**Indexing:** default is fine. If RU use matters later, add a composite index on `(status, checkedInAt)` for selection and `(status, checkedOutAt)` for the digest.

**Lifecycle:** **updated in place**, **soft-deleted** (status `checkedOut`). Units are never deleted.

## Container: `pushSeen` (#77)

Short-lived documents, partitioned by **`/eventKey`**, each with its own **`ttl`** (the container's default is a day), so Cosmos deletes them itself.

A person counts as having seen an event if any of their devices sent a receipt; a delayed push can leave them out.
- **Push job claims:** `{ "id": "job:<jobId>", "eventKey": "job:<jobId>", "claimedAt": "…", "ttl": 691200 }`. Created (never upserted) when a queued push job runs, so a re-delivered queue message finds it and sends nothing (8 days: longer than the queue keeps messages).

A change creates it (create-only, so two at once conflict and one retries) or joins it (ETag replace; a key already there is skipped). It falls due 60 s after `lastAt`, but no later than 5 minutes after `firstAt`. Sending **deletes** it (ETag delete), so a stale or re-delivered queue message finds nothing to send, and the next change starts a new batch. At most 200 changes. Each change may also carry `actorName` (the person's display name, #89, for "Checked out by Sam").

- **A sent batch** (#89): the same shape as `{ "id": "batchSent:<batchId>", "eventKey": "batchSent:<batchId>", "type": "stockChangeBatchSent", …, "ttl": 259200 }`, upserted just before the pushes go, so tapping a push can show what was removed (`GET /api/run-out/batches/{batchId}`). Kept 3 days.

## Change-feed flow

The API Function app processes new scan events through a Cosmos DB trigger on `scanEvents` (with the `leases` container). Ingest does not do any of this.

```
Pi ──POST /api/scans──▶ Ingest ──▶ scanEvents (create, id = scan ID)
                                   devices    (upsert)

scanEvents change feed ──▶ API Function (processor), for each new event:

  role = in:
    0. store-labelled barcode (EAN-13 starting 20–29)? ──▶ skip (later feature)
    1. products.read("barcode:<barcode>")
         found ──▶ productId = lookup.productId; products.read(productId)
                     known / noMatch      ──▶ use it (no Open Food Facts call)
                     lookupFailed         ──▶ retry Open Food Facts once, update product
                     missing (see below)  ──▶ as "not found", with this productId
         not found ──▶ claim: products.create barcode lookup
                         (id = "barcode:<barcode>", productId = new GUID), create-if-not-exists
                         conflict ──▶ lost the race: read the winner's lookup, use its productId
                       Open Food Facts lookup
                         found             ──▶ products.create product (known)
                         not found         ──▶ products.create product (noMatch, "Unknown item (<barcode>)")
                         transient failure ──▶ retry (back-off); still failing ──▶
                                               products.create product (lookupFailed, "Unknown item (<barcode>)"), error logged
                       (product create is create-if-not-exists on productId: a conflict means
                        the race winner already created it, so read it)
    2. inventoryItems.create unit (id = scan ID, partition productId; conflict = already processed, skip)
    3. notifications (scan feed / SignalR) ──▶ later feature

  role = out:
    1. products.read("barcode:<barcode>")
         not found ──▶ unmatchedCheckOuts.create (productId null)
         found     ──▶ select one inStock unit of lookup.productId (see unit selection)
                         found ──▶ mark checkedOut (ETag-guarded), set checkOutScanId
                         none  ──▶ unmatchedCheckOuts.create (with productId)
    2. notifications ──▶ later feature

Lookup-retry timer (every 15 minutes):
    products where type = product and status = lookupFailed, oldest lastLookupAttemptAt first, at most 10
      ──▶ retry Open Food Facts ──▶ known / noMatch / lookupFailed (lookupAttempts + 1)
```

**"Lookup document but no product":** the claim (barcode lookup) is written before the product. If the processor stops between the two, the replay finds the lookup with no product and carries on as for a new barcode, using the claimed `productId`. The same happens to the loser of a race that reads the lookup before the winner has created the product; at worst Open Food Facts is called twice, and the second product create conflicts and reads the first.

The change feed is **at-least-once**, so every step must be safe to repeat. See Idempotency.

## Unit selection on check-out

When a product has several units in stock, a check-out takes **one**, chosen by:

1. Among the product's `inStock` units, **opened units first** and units **in the freezer last** (#65).
2. Then **soonest `estimatedExpiryDate` first** (units with an estimate before units without).
3. Ties and units with no estimate: **oldest `checkedInAt` first** (FIFO).
4. Final tie-break: lowest `id`, so the choice is deterministic.

This is "use the oldest stuff first". While no expiry dates exist, it is plain FIFO. The units are selected by **product**, so a check-out with any of a product's barcodes takes from all of that product's units.

**Concurrency:** two quick check-outs of the same product must take two different units. The update is conditional on the unit's `_etag`. On conflict, the processor re-reads and tries the next candidate.

## Idempotency

**Scan ID:** the Pi generates a **UUID v4 per scan** at the moment it reads the barcode, before queueing. It is the scan event's `id`, and it travels with the event through retries and resends.

| Situation | What happens |
|---|---|
| Pi resends a scan (timeout, lost response, queue replay) | Ingest `create`s with `id = scan ID`. A conflict is treated as success and returns the same 2xx. One document stored. |
| Change feed replays a check-in | The barcode resolves to the same `productId` (lookups are never repointed), so the unit create (`id` = scan ID, same partition) conflicts and is skipped. |
| Change feed replays a check-out | Before acting, look for a unit of the product with `checkOutScanId = scan ID`, or an unmatched check-out with `id = scan ID`; if found, do nothing. The unmatched check-out create also conflicts on its own. |
| Two scans of the same tin | Two different scan IDs, so two units. This is intended ("one unit per scan"). |
| Two scans of a **new** barcode at once | The barcode lookup create-if-not-exists lets only one claim it; both units get the same `productId`. One product. |
| Product lookup repeated | Barcode lookups and products are create-if-not-exists; products with a final answer are never overwritten. |

Note this means a *genuine* second scan is never mistaken for a resend, because the ID is minted per read, not derived from barcode + time.

### Meal plans in `savedRecipes` (#119)

The same container and partition (`householdId: "household"`) also holds the household's **meal plans**: one document per plan, `type: "mealPlan"`, `id` = the plan's id (a UUID), the plan exactly as `GET /api/meal-plans/{id}` returns it (docs/api.md, Plan meals) plus `householdId` and `type`. **No `ttl`:** plans are kept until deleted (#126 adds the button). Written ETag-checked (create-only the first time, then replaced under the ETag; a change made while another runs is a 409). Saved recipes are read with `WHERE c.type = 'savedRecipe'` (and a saved recipe's id never returns a plan), so the two never mix. A meal holds `recipe` (the full recipe once written, #126, kept as given so a kept meal keeps it), `uses` / `usesUp` as product ids with the name they had when the plan was made, `toBuy` as short generic names, `keep` and `warnings`. `addedToListAt` is for #125.

A new plan is created `generating` and a `{ planId }` message goes on the `meal-plan-jobs` queue in the API app's storage account (created on first use by its identity); the queue-triggered job writes the meals and saves the plan `ready` or `failed`. No infra change.

**"Usually buys" reads** (best effort, about 17 RU on today's data): `inventoryItems` `SELECT productId, checkedInAt, checkedOutAt WHERE checkedInAt >= @start OR checkedOutAt >= @start`; `products` `SELECT id, displayName, genericName WHERE type = 'product'` (only when the first returned rows); `shoppingList`, partition `household`, `SELECT name, timesAdded, aisle WHERE type = 'memory'`. ## Container: `settings` (#120)

Settings people change in the app, one document each, partitioned by **`/id`**. Today there is one: **`aiModels`**, the Foundry models the household has registered and which one each job uses. Written under its ETag (create-only the first time). No `ttl`.

```json
{
  "id": "aiModels", "type": "aiModels",
  "models": [{
    "id": "luna", "label": "GPT-6 Luna", "deployment": "gpt-6-luna",
    "temperatureMode": "default", "jobs": ["recipes"],
    "addedBy": "<oid>", "addedByName": "Gary", "addedAt": "2026-10-27T09:00:00.000Z",
    "tests": null
  }],
  "active": {
    "recipes": { "modelId": "luna", "changedBy": "<oid>", "changedByName": "Gary", "changedAt": "…", "previousModelId": "gpt-4o" }
  }
}
```

- **`deployment`** is the **deployment name as shown in Foundry** (the key in `/openai/deployments/<name>/…`, not necessarily the model's name). Nothing here creates or lists deployments in Foundry: a model must already be deployed.
- **`temperatureMode`:** `usual` sends each caller's own temperature (0.7 or 0.9 for recipes, 0 for photos and generic names); `default` leaves `temperature` out, for a model that only accepts its default (gpt-6-luna). New models start as `usual`; the test suite (#121) sets it.
- **`jobs`:** which jobs the model has passed tests for (`recipes`, `photos`, `genericNames`); empty until tested (#121). A model can only be made active for a job it passed. **`tests`** holds the latest test results (#121), kept as given.
- **`active`:** one entry per job, only for jobs that have been given a model. A missing entry (or no document) means the job uses its **default**: the `RECIPE_MODEL_DEPLOYMENT`, `PHOTO_MODEL_DEPLOYMENT` or `GENERIC_NAME_MODEL_DEPLOYMENT` app setting, else `gpt-4o`, with the usual temperature. `previousModelId` (null: the default) is what **revert** goes back to.
- **Reading:** each Foundry call resolves its job's model per request, from a copy cached for a minute on each app instance (a write clears the copy on the instance that made it), so a change reaches every instance within about a minute. If the document can't be read, the last good copy is used, else the defaults: a settings problem never stops a recipe.
- At most 20 models; deployment names are unique (ignoring case).
- **Seeding:** until the test suite (#121) sets `temperatureMode` and `jobs`, `deploy/seed-ai-models.sh` registers the models in `deploy/ai-models.seed.json` and sets them (as the person running it; never touching `active`).

### Model test runs (#121)

A run of the model test suite is a short-lived document in the **`pushSeen`** container (partition `/eventKey`, per-document `ttl`), so Cosmos deletes it itself:

- **`testrun:<runId>`** (`type: "modelTestRun"`, `ttl` one day): the run as `GET /api/settings/ai-models/test-runs/{runId}` returns it (docs/api.md, Model tests). Created `queued` by the start request, claimed under its ETag by the queue-triggered function (`queued` → `running`), saved after each check, and finished `done` (or `failed`).
- **`testrun-active:<modelId>`** (`type: "modelTestActive"`, `ttl` 20 minutes): `{ runId }`, created while a run is in progress (a second create conflicts, which is how a second start gets the running one) and deleted when it finishes.

The finished run is also saved on its model in `aiModels` as **`tests`** (the same shape), with the model's `jobs` and `temperatureMode`. Run state never goes in the settings document while a run is in progress. The queue (`model-test-runs`) and the test image (blob container `model-tests`, `pack.png`) are in the API app's storage account, created on first use by its identity (Storage Queue Data Contributor, Storage Blob Data Owner): no infrastructure change.

## Measuring Cosmos (#115)

Every Cosmos call either app makes is measured, for Faster back end (#96) and the cost guard (#107). Nothing changes what's read or written. KQL for each view is in [`tools/perf/queries.kql`](../tools/perf/queries.kql).

- **How:** a Cosmos SDK request handler (`CosmosMetricsHandler`, on the one `CosmosClient`) sees every point read, create, upsert, replace, patch and delete. Queries through `CosmosJson.QueryAsync` are recorded **once per query**, over all their pages. A query sent any other way is recorded per page as `<container>.query`.
- **Per call:** the operation name, container, RU charge (`RequestCharge`, summed over pages), items, pages, duration, partition scope (`single` / `cross`) and HTTP status (a 429 shows only once the SDK's own retries are spent). These go to App Insights as **pre-aggregated metrics** (`Cosmos RU`, `Cosmos duration ms`, `Cosmos items`, `Cosmos pages`; table `AppMetrics`, one row per minute per operation, container, scope and status), never one log line per call. **No document content, ids or query parameters.**
- **Per invocation:** `CosmosUsageMiddleware` in each app totals the RUs and calls of each HTTP request and each timer, queue or change-feed run (an `AsyncLocal` per invocation). Reported as the metrics `Cosmos RU per invocation` / `Cosmos calls per invocation` by function and trigger, and one trace per invocation that touched Cosmos, `Cosmos usage: <function> (<trigger>) made n Cosmos calls costing x RU` (properties `Function`, `Trigger`, `CosmosCalls`, `CosmosRu`), carrying the request's operation id. In the isolated worker the request row itself is written by the host, so the totals sit on this correlated trace rather than on the request.
- **Index metrics:** while the app setting `COSMOS_INDEX_METRICS` is `true`, queries ask Cosmos for index metrics (`PopulateIndexMetrics`), and each operation's are logged at most once an hour: `Cosmos index metrics for <operation>: …` (properties `CosmosOperation`, `IndexMetrics`: the utilised and potential single and composite indexes, as paths only).

**Operation names.** Point operations: `<container>.<verb>` (`read`, `create`, `upsert`, `replace`, `patch`, `delete`), e.g. `products.read`, `inventoryItems.replace`. Queries: `<container>.<calling method>`, without `Get` and `Async`:
